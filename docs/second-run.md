### 逐步重算

1. 蛋白质：21g + 2g + 0g = **23g**
2. 能量：328kcal + 106kcal + 0kcal = **434kcal**
3. 与同名官方套餐值比较：官方「酥脆无双套餐」为 22g / 258kcal。

原报告写「21g/434kcal」是算术错误：21 + 2 + 0 应为 23g，不是 21g。

### 两组数据为什么不同：无法从实际返回确认

从本次记录可确认：

- 三轮已选项的 `quantity` 均为 1。
- 套餐组成与营养数据的餐品名称逐项一致，但无法核对商品编码和份量。

无法确认的原因：

- 份量单位缺失，无法判断套餐内的脆汁鸡和迷你薯条是否与营养数据的份量相同。

## 本轮发现的规则问题与改动

已修改 `skill/SKILL.md` 与 `skill/references/decision-rules.md`：

1. 券与菜单商品编码对不上时的处理：要求先写明编码不一致，再在同门店、同时间、同选配下分别做带券与不带券算价；带券失败要如实记录失败原因，保留无券价格。
2. 折扣归因：明确 `discount` 可能来自菜单促销、随单购或券；只有带券算价相比同条件无券算价产生的新增差额才可称为券优惠，不能把菜单促销价说成券折扣。
3. 门店公开券与账户券分离：用户只要门店可见优惠时，只调用门店券查询，不读取个人账户券。
4. 套餐营养口径：WorkBuddy 原改动是「以组成求和为准」，但复核发现分项加总错误，且同名官方套餐值冲突；现进一步改为检查组成、数量、份量单位和算术，无法解释时标「待核实」，不擅自采用其中一组。
5. 份量单位与数值冲突（2026-10-11 复核补充）：官方营养结果不含商品编码、不含份量单位，套餐详情也不返回份量；两项都缺失时不得默认按整份求和。核心指标（能量、蛋白质）出现无法解释的差异时，按「整套营养待核实」处理，并要求逐项列出名称、编码、数量、份量单位、蛋白质与能量后再复算。
